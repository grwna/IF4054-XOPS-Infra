## Tech Stack
- Kind, kubectl, Helm, Kyverno, metrics-server
- Terraform (cluster + namespaces + ingress-nginx + Kyverno + metrics-server)
- Ansible (host bootstrap: tools, cloudflared, GitLab Runner)
- GitLab CI/CD (runner on same host as cluster)

## Bootstrap vs Pipeline

**Day 0 (once, manual):** ansible installs host tools + registers runner. Host is bootstrapper concern — can't be in CI because runner must exist before any job runs.
**Day 1+ (every push):** pipeline deploys ALL infra via CI/CD (spec requirement): terraform (cluster/platform), Kyverno policies, Helm chart (dev auto, prod manual gate).

Terraform state on host (`/root/tfstate`, mounted into runner jobs) — persists across runs, no cluster recreate. Ansible/cloudflared/runner config never touched by pipeline.

## How to Use

### Day 0 - Bootstrap (once)

- Install SSH and Ansible:
```bash
sudo apt install openssh ansible

# or

chmod +x init.sh && sudo ./init.sh
```

- Fill `vars.yaml` (copy `vars-example.yaml`, set `cf_token` + `gitlab_token` glrt- runner token), then:
```bash
sudo ansible-playbook server-setup.yaml
```

- Verify tools + runner container:
```bash
kubectl version --client
kind --version
terraform version
docker ps
```

Cluster + platform (kind, namespaces, ingress-nginx, Kyverno, metrics-server) is created by the **pipeline** on first push (`terraform_apply` job) — no manual terraform needed. Fallback if CI bootstrap fails, run locally:
```bash
sudo terraform init
sudo terraform apply -target=kind_cluster.xops -auto-approve
sudo terraform apply -auto-approve
```

Note: runner must be **re-registered** once after `/root/tfstate` mount was added (jobs need the volume):
```bash
docker exec gitlab-runner gitlab-runner unregister --all-runners
sudo ansible-playbook server-setup.yaml
```

### Restart after shutdown

After WSL/server reboot - no ansible, no terraform needed (state on disk):
```bash
chmod +x start.sh && sudo ./start.sh
```
Starts docker, kind node, gitlab-runner, cloudflared. See comments in `start.sh` for when NOT to use it (first setup / deleted cluster = redo day 0).

### Day 1+ - Pipeline

Push to repo. Runner (same host) picks jobs. Stages:
1. `validate` - kyverno CLI test on policies
2. `deploy-cluster` - terraform apply (kind + ns + ingress-nginx + Kyverno + metrics-server)
3. `deploy-infra` - kubectl apply Kyverno ClusterPolicies
4. `deploy-dev` - helm upgrade to `dev` namespace (auto)
5. `deploy-prod` - helm upgrade to `prod` (manual gate, `main` only)

If jobs stuck "no runner": runner must have tag `xops` (GitLab UI > Settings > CI/CD > Runners > Edit runner > Tags).

## Manifests & Kyverno Policy

The section below documents the finished manifests + Kyverno policy scope
for `retail-store-app-xops` (AWS retail-store-sample-app, 5 microservices:
`ui`, `catalog`, `cart`, `orders`, `checkout`). Cluster provisioning, the
infra CI/CD pipeline above, and the prod approval gate are a separate scope.

See **[docs/policy-design.md](docs/policy-design.md)** for the full design
rationale, the gap analysis against the upstream app charts, and the
evidence that the policies actually reject what they're supposed to.

## Layout

```
helm/
  charts/           vendored + patched copies of the app's per-service Helm
                     charts (cart, catalog, checkout, orders, ui) and the
                     umbrella chart that wires them together
  values/
    dev.yaml         environment overlay: image tag, autoscaling, ingress host
    prod.yaml
kyverno/
  policies/          6 ClusterPolicy files, one per enforced requirement
  tests/
    kyverno-test.yaml      declarative test suite (kyverno test)
    resources/              1 compliant + 7 single-violation fixtures
rendered/            `helm template` output per environment (generated by
                     scripts/render.sh; gitignored — regenerate locally,
                     see "Reproduce" below)
scripts/
  render.sh           renders helm/charts/app -> rendered/{dev,prod}.yaml
docs/
  policy-design.md    design doc + requirement-to-policy mapping
  evidence/           kyverno test/apply output, saved as proof
```

## Requirements

- `helm` (brew install helm)
- `kyverno` CLI (brew install kyverno)
- no cluster needed — everything below runs offline against rendered YAML

## Reproduce

```bash
# render dev + prod manifests from the vendored charts
./scripts/render.sh

# check the real manifests against all 6 policies (expect 0 fail)
kyverno apply kyverno/policies/ --resource rendered/dev.yaml --policy-report
kyverno apply kyverno/policies/ --resource rendered/prod.yaml --policy-report

# run the full positive/negative fixture test suite (expect 48 passed, 0 failed)
kyverno test kyverno/tests/
```

## What's enforced

| Spec requirement | Kyverno policy |
|---|---|
| Non-root container | `require-run-as-nonroot` |
| Read-only root filesystem | `require-readonly-rootfs` |
| No privilege escalation | `disallow-privilege-escalation` |
| CPU + memory resource limits | `require-resource-limits` |
| Liveness **and** readiness probes | `require-liveness-readiness-probes` |
| Image only from group's registry | `restrict-image-registries` |

Autoscaling, dual image tags, and prod approval are satisfied by chart
values + the CI/CD pipeline rather than by Kyverno — see
[docs/policy-design.md §4](docs/policy-design.md#4-kyverno-policies) for why.
